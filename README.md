# 选中解释 / dsh-explain-selection

选中 DSH 回答里的任意文本 → 右键「解释」→ 贴着选区弹出讲解卡片；卡片里的文字**照样可以选中再解释**，可无限层。
解释由宿主**直接调用 `ctx.llm` 流式生成，不写入会话日志、不进入主对话上下文**——套娃刷屏的问题从根上消失。
定位是**即时学习**：答案短、响应快、重复查询零消耗。

## 安装

```bash
dsh plugin add github:KLAX54ix/dsh-explain-selection
```

桌面端（DSH Desktop）的 `desktop` profile 由 Electron 应用独占管理，命令行添加会被拒绝——
请在应用内 **设置 → 插件 → 添加插件** 里填同一个地址：

```
github:KLAX54ix/dsh-explain-selection
```

- **客户端半体**改动会**自动热加载**。
- **宿主半体**（`index.js`）改动**必须重启应用**才生效，原因见下文「宿主半体的改动必须重启应用」一节。

## 结构

| 文件 | 作用 |
|---|---|
| `package.json` | bundle 清单：`dsh.bundle.patch`（宿主行）+ `dsh.client`（浏览器半体） |
| `cordis.patch.yml` | 向 Loader 插入宿主行 `explain-selection` |
| `index.js` | 宿主半体：受鉴权的 `/api/explain.selection`，NDJSON 流式返回 |
| `client.js` | 客户端半体：选区工具条、锚定卡片、流式渲染、递归解释、答案缓存 |

两半体走 DSH 官方的 Connection Fetch 通道，与内置 `/api/session.export` 同一套机制：
宿主 `ctx.connection.fetch.register({ path: '/api/…' })`，浏览器按**文档相对路径** `api/…` 发起 `fetch`。
（这条通道受浏览器鉴权保护：无令牌的本地请求得到 `401 unauthorized`。）

## 性能与成本设计（关键）

### 1. 必须显式关闭推理

DeepSeek 适配器在 `purpose` 不是 `'session-title'` 时，推理强度**默认 `high`**：

```js
// dsh-llm-deepseek/lib/index.js:1694
const effort = options.purpose === "session-title" ? "off"
             : options.reasoningEffort ?? connection.defaults.reasoningEffort
               ?? (connection.defaults.thinking === "disabled" ? "off" : "high");
```

而 `max_tokens` **同时覆盖推理与答案**（同文件 `max_tokens: options.maxTokens ?? …`）。
所以不关推理时，512 的预算会被推理吃光 → 每张卡片都返回 `max-tokens` 结束原因、内容被截断，而且又慢又贵。

本插件显式传 `reasoningEffort: 'off'`（合法取值 `off | low | high | max`）：
适配器随即发送 `thinking: { type: 'disabled' }` 且不带 `output_config`，**推理完全不发生**。
若要质量优先，把它改成 `'low'` 即可（一行）。

### 2. 输入输出双向收紧

| 参数 | 值 | 理由 |
|---|---|---|
| `reasoningEffort` | `'off'` | 去掉全部推理 token |
| `maxTokens` | `256` | 只是安全上限；关掉推理后模型自己就会停 |
| 输入上限 | `400` 字符 | 查一个术语或短句够用，超出部分截断 |
| 上下文窗口 | 前后各 `120` 字 | 消歧用，约 +160 输入 token；`CONTEXT_RADIUS` 一个常量可调 |
| 提示词硬约束 | 「两句话以内，最多 80 字」 | 宁短勿长 |
| 系统提示词 | 约 110 token | 每次调用都要付，所以写得极短 |

粗算单次成本：短术语查询约 **280 输入 token**（系统提示 + 选中的词 + 上下文窗口），
输出通常 60~100 token；缓存命中为 **0**。

### 3. 客户端答案缓存

同一片段再次解释**直接命中缓存**：不发请求、不耗 token、瞬时显示。
嵌套追问会反复回到同一个词，这一层收益最大。缓存按规范化文本（折叠空白）为键，上限 200 条，FIFO 淘汰。
只缓存**完整且无错**的回答，中断或报错的部分结果不入缓存。

### 4. 上下文（会联系上下文解释）

**缓存键已包含上下文**：键是 `文本 \0 上下文 \0 父术语`。
否则同一个词换一句话会命中上一条缓存，你会拿到上一个语境的（可能错误的）答案。

### 提示词里规则顺序是承重的

第一版把规则写成「2. 先说它是什么」+「5. 结合【原文片段】…」，
结果**第 2 条压过了第 5 条**——「先说它是什么」是一句*词典定义*指令，
模型即便拿到了原句，也会老老实实给一个通用释义。

现在上下文规则排在第 1 条，并且**删掉了任何要求"抽象地说它是什么"的措辞**：

```
1. 有【原文片段】时，先判断这个词在它里面指什么，只讲这个意思，不要罗列别的含义。
2. 两句话以内，最多 80 字，宁短勿长。
...
5. 线索不足就直说常见含义，不要假装确定。
```

### 卡片会自证：上下文到底送到没有

宿主每个回答的第一条事件是 `{type:'meta', contextChars, parentChars}`，
卡片底部据一条浅灰行显示实际附带了多少消歧信息：

| 你看到 | 含义 |
|---|---|
| `已带上下文（上下文 240 字）` | 客户端附了、宿主也确认收到了 |
| `已带上下文（…） · 宿主未确认，请重启应用` | 客户端附了，但**宿主半体是旧版**，把字段丢了 |
| 没有这一行 | 本次切词没有可用的上下文（例如选区在很短的片段里） |

这一行是刻意留的：它把"**模型没用上下文**"和"**上下文根本没送到**"分开——
这两者的修法完全不同，不显示出来就只能靠猜。

### ⚠️ 宿主半体的改动必须重启应用

`index.js`（宿主半体）**不会**随页面刷新热更新，只有 `client.js` 会。
上下文字段与提示词都在 `index.js` 里，所以**改过之后必须重启 DSH**，
否则客户端照旧发送、宿主照旧丢弃，看起来就像"上下文功能没用"。

两种来源：

| 场景 | 上下文 | 是否读 DOM |
|---|---|---|
| 在正文里选中 | 选区所在散文块的**前后各 120 字** | 读（见下） |
| 在卡片里选中 / 点术语 | **父卡片自己的解释文本** + 父术语 | 不读 |

嵌套时不去读 DOM：父卡片那段解释本身就是最好的语境，直接复用，更准也更省。

**窗口用 Range 的字符偏移定位，不用 `indexOf` 找选中文本。**
`rawOffsetOf()` 用 `TreeWalker` 数出选区起点在散文块里的精确字符偏移。
若改用 `textContent.indexOf(选中的文字)`，同一个词在同一段里出现两次时会**永远取到第一处**的前后文——
喂给模型的【原文片段】和真实选区错位，而且答案看起来毫无异常。

配套的一个坑：偏移量索引的是**原始文本**，所以必须切原始文本、只对切出来的片段做空白规范化。
先把空白折叠再按偏移切，每个偏移都会错位。

**定位失败时宁可不给上下文。** 若 Range 边界不是文本节点（如整块选择），窗口无法定位：
此时只有"散文块本身足够小、整块就是上下文"才安全，否则返回空——
错误的上下文比没有上下文更糟，它会让模型自信地答错。

宿主收到的字段各自封顶：`MAX_CONTEXT_CHARS = 400`、`MAX_PARENT_CHARS = 120`，
客户端传什么都越不过去。

### 上下文带来的新失效模式：为非词编造含义

**真实案例。** 选中「浮动工具条」中间的「动工」两个字（跨词边界的相邻字，本身不是词），
当时的回答是：

> 「动工」在这里指开始实际修改代码，也就是把重写方案真正落地跑起来。

这是**上下文注入引入的新错误**，而且比"给通用释义"更糟——它错得很自信、很贴题。

根因在提示词：当时的第 1 条是「先判断**这个词**在【原文片段】里指什么」，
**它预设了选中内容是个词**。模型于是被迫在代码语境里编一个自洽的含义。

修复：**提示词新增第 1 条**，把"是不是词"的判断提到最前，并明确允许拒绝：

```
1. 先判断选中的文字是不是一个独立的中文词或术语。若它只是跨词边界的片段、
   代码标识符或不成词，直接说明它不是一个词，并指出它原本属于哪个词；严禁为它编造含义。
2. 是词时，有【原文片段】就按它判断它在这里指什么，只讲这个意思。
```

**曾经试过、已被否决的做法：分词吸附。**
一度用 `Intl.Segmenter('zh', {granularity:'word'})` 把落在词中间的选区自动扩到完整词，
想从源头避免把跨词片段送出去。**已移除**——原因是它违背了最基本的预期：
**标记只应覆盖用户真正选中的字**。用户选了「动工」，屏幕上却在「浮动工具条」上高亮，这是不能接受的。

所以边界划在这里：

| | 范围 |
|---|---|
| **被解释的文本**（卡片标题、原文标记、送给模型的 `text`） | **严格等于用户的选区**，绝不扩宽 |
| **上下文**（`contextWindow`，送给模型的 `context`） | 前后各 120 字，**只作参考，不改变选区** |

非词怎么办？交给提示词第 1 条去拒绝，而不是靠改用户的选区来回避。

**一处有意的偏离**：取顶层选区窗口时，会**读**（绝不写）选区所在散文块的文本。
官方 practices 禁止的是"读别人的 DOM **来估算定位**"，而这里是为了消歧、只读不写、且有硬上限。
这是本次实现里唯一一处灰色地带，单独记录在此。

### 5. 渲染节流

流式 token 不再逐个提交。每个 delta 只写入 `pendingRef` 缓冲，并用 rAF 合并成**每帧最多一次** `setCards`。

原因：原本每个 token 一次 `setCards` → overlay 全量重渲染 → 每张卡片一次 `getBoundingClientRect()` + 定位计算。
开 3~4 张卡快速流式时，那是**每 token 一轮强制布局**。
现在渲染回到浏览器自己的节奏上。收尾时（正常结束 / 报错 / 中断）会先 `flushDeltas()` 再改状态，
否则最后一帧缓冲的文本会被丢掉。

### 6. 锚点统一

卡片和工具条都通过 `anchorRect(range, fallback)` 取**实时**位置，`fallback` 只在节点被替换后兜底。
工具条原本用的是选中时固化的 `picked.rect`，滚动后卡片跟上了、工具条还浮在旧视口坐标上——
现在两者走同一条路径。锚点滚出视口时工具条自然落到视口外（无需额外逻辑），滚回来即恢复。

### 7. 会话作用域生命周期（跨会话残留的修复）

**曾经的严重 bug**：切换项目/会话后，旧会话的卡片仍浮在屏幕上。

根因是作用域错配：`shell.overlay` 是 **root 作用域**的全局浮动层，**不随会话卸载**，所以卡片状态一直活着。
旧会话的 DOM 被卸载后，它的 `Range` 变成游离节点，`getBoundingClientRect()` 返回零矩形，
`anchorRect` 于是退回**选中时固化的那个视口坐标**——卡片就留在原地，压在新会话上面。

修法：**用 session 作用域的注册去驱动 root 作用域的浮层**。

`SessionScopeProbe` 是一个不渲染任何东西的组件，注册进 `conversation.input.dock`（**session 作用域**）。
它同时提供两个信号：

1. **会话身份**：该 slot 的 props 里带 `sessionId: SessionId`（这是 slot 目录里文档化的，
   而 `shell.overlay` 的 standardProps 里**没有** sessionId——这正是浮层自己看不到会话变化的原因）。
2. **拆解时机**：会话切换时 slot 系统必然卸载该条目，`useEffect` 的 cleanup 会报告"会话已消失"。

两者都汇入 `reportSession()`：**身份一变，销毁全部卡片**、原文标记与进行中的请求。

**卡片用完即销毁，不做任何保留。** 这是有意的选择，也写在这里避免以后又被"顺手优化"回去：

- 试过**按会话归档**（切走存内容、切回放进右下角抽屉）。已**否决并移除**。
  理由是成本与复杂度不划算：对话 DOM 重建后 `Range` 失效，归档回来的卡片**既不能钉在原文上、
  也不能有原文标记**，只能收进一个平行于卡片的第二显示面（抽屉）。多一套 UI、多一套状态，
  换来的只是一份脱离原文的文字。
- 所以现在的语义是最简单的那个：**卡片属于"这次阅读"，离开即销毁**。
  重新解释的成本很低（有缓存时瞬时，无缓存也就一次几十 token）。

**孤儿兜底**（`isAnchored(card)`）：锚点全部游离时直接删除卡片（fork、切工作区、面板重建）。
只处理"全死"是因为单个锚点可能因 React 换节点而瞬时游离，为瞬时状态删掉用户正在读的卡片更糟。

## 交互

- **右键菜单**：选中文本 → 右键 → 菜单里 **解释** 与 **复制** 并列。选中本身不再弹出任何东西。
- **解释**：开一张贴着选区的卡片；流式输出。
- **复制**：走 `navigator.clipboard.writeText`；成功后短暂显示「已复制」再自动关闭。
- **嵌套（两种方式）**：
  1. **点术语**：模型输出里的 `[[术语]]` 标记会渲染成带虚线下划线的可点词，点一下就在它旁边开一张新卡片。
  2. **选中 + 右键**：卡片正文里任意文字都能选中，走同一个菜单再开一张。
- **拖动**：抓住卡片头部拖动即可把卡片停在任何位置（头部是拖拽手柄，正文仍可正常选中）。
- **拖拽时的指向线**：见下节。
- **收起 `–` / 展开**：收起后变成贴着原锚点的小胶囊，点击展开。详见下节的「胶囊一定回到原文」。

### 胶囊一定回到原文

**它曾经会站错位置。** 第一版里胶囊复用了卡片的位置来源（拖拽中 → 停靠位置 → 锚点），
于是**你拖走一张卡片再收起它，胶囊会留在你拖到的地方**，而不是回到选中文本旁边——
对一个"最小化标记"来说这是最不该发生的事。

现在分三处处理：

1. **胶囊永远只用 `placeChipBeside(rect)` 锚定原文**，完全不读 `pinned` / 拖拽位置。
2. **收起时同时清除停靠位置**（`delete next.pinned`），所以从胶囊展开回来的卡片**也落在原文处**，
   不会"胶囊在原文、卡片瞬移回你拖到的角落"。
3. **不再用 260px 估算胶囊宽度**。第一版调的是 `placeBeside(rect, 260, 30)`，
   把胶囊的**上限**当成布局宽度预留：锚点靠近右边缘时，
   胶囊会被硬推到文本左边**最多 260px**——这也是"没有回到正确位置"的一个来源。
   现在只预留一个最小值（`CHIP_MIN_WIDTH = 96`），并把上限**按剩余空间**算出来：

   ```js
   maxWidth: `min(260px, calc(100vw - ${left}px - 8px))`
   ```

   于是胶囊既能贴着文本左边缘，又不会溢出屏幕，而且**不需要测量元素**。

- **关闭 `×`**：移除卡片并 `abort()` 请求；宿主检测到断流后**立刻停止拉取模型流**，不白烧 token。
- **关闭菜单**：点击别处、滚动、缩放窗口、Esc。
- **跟随**：卡片锚定在选区的 `Range` 上，滚动/缩放自动跟随；贴近底部时自动翻到选区上方。
- **原文标记**：见下节。

## 拖拽与指向线

**卡片可以拖走**：抓住头部左侧的 `⣿` 手柄（`cursor: move`）拖到任意位置，松手即停在那里，不再跟着原文跑。
手柄是**独立元素**，和收起/关闭按钮是**兄弟节点**——按钮不在手柄内，按按钮永远不会进入拖拽逻辑。
正文仍然照常可选中——这是嵌套解释的入口，不能被拖拽抢走。

### 拖拽中可以用滚轮滚页面

按住卡片不放时，**滚轮仍然滚动对话**，方便把卡片放到当前看不到的位置上。

这一条不是顺手就有的，而是**必须专门处理**的：浮层在 `shell.overlay`，官方定义是
"Frame-wide floating layer, above every column and **outside their scroll containers**"。
所以鼠标悬在卡片上滚轮时，事件会沿浮层自己的 DOM 祖先链冒泡到 `body`，
**根本到不了对话的滚动容器**——这是浮层位置的必然结果。

**解法**：拖拽期间给被拖的卡片加 `pointer-events: none`。

- 手势本来就在 `document` 上跟踪，**卡片不接收任何指针事件也能被拖动**
- 于是滚轮**穿透**到下面的对话，浏览器**原生**滚动它
- 我们**没有写任何 wheel 监听器**，也不去动别人的 `scrollTop`——没有任何越界操作别人 DOM 的行为

两个附带效果：

- 卡片是 `position: fixed`，滚轮不改变指针坐标，所以**卡片停在原地、内容在下面滚过**——
  这正是"先滚到目标附近再放手"所需要的。
- 指向线跟着更新：滚动触发既有的 `onViewportChange`（capture 阶段监听，能收到嵌套容器的滚动），重算锚点后虚线自动重定向。

**一点外观代价**：拖拽期间指针落在下面的内容上，光标会变成文本光标而非 `move`。
要保住 `move` 就得往 `document.body` 写样式，属于动别人的 DOM，所以没做。

**问题**：一旦卡片可以自由摆放，屏幕上就再没有东西说明"这张卡讲的是哪几个字"。
拖三张卡之后就变成一堆匿名便签，这正是要避免的"乱七八糟"。

**解法**：**拖拽时画一条较淡的虚线，从卡片指回它解释的那段文字**，
并在文字那一端点一个 2.5px 的圆点，标出确切位置。

| 细节 | 取值 | 理由 |
|---|---|---|
| 线型 | `stroke-dasharray: 5 4`，`stroke-width: 1` | 虚线＝引导，不与内容争视觉 |
| 颜色 | `--dsw-alias-brand-primary`，`stroke-opacity: 0.4` | **较淡**，跟随主题 |
| 层级 | `z-index: 2`（卡片是 3） | 线从卡片边缘出发，且**永远不会横穿别的卡片** |
| 端点 | 用 `edgePoint()` 求"从矩形中心指向目标时与边界的交点" | 线首尾都停在边框上，不钻到卡片或文字底下 |
| 出现时机 | 指针位移 > 3px 之后 | 单纯点一下头部不该闪出一条线 |

**嵌套卡片自动正确，不需要额外映射。** 子卡的 `Range` 指向的是**父卡片 DOM 里那个术语 span**，
所以父卡被拖走时 DOM 移动、`getBoundingClientRect()` 跟着变，指向线**自己就跟着重定向了**。
父卡被钉在别处、甚至父卡本身也在被拖动时，同理成立。

**指向不存在的东西时宁可不画**：用 `isAnchored()` 检查锚点是否仍在文档里。
孤儿卡片的 `rect` 是固化的旧视口坐标，画一条指向虚空的线比不画更糟。

**回到原文**：被拖走的卡片头部会多出一个 `⤺` 按钮；也可以**双击头部**。
（`beginDrag` 里刻意**没有** `preventDefault`——它会抑制兼容鼠标事件、连带干掉 `dblclick`，
所以按钮才是可靠路径，双击只是顺手。）

## 跟随语义：谁跟着谁动

这里有**两条互相独立的规则**，一开始我把它们混成了一条，结果自相矛盾：

| | 规则 | 依据 |
|---|---|---|
| **位置** | 锚定的卡片跟随锚点；**停靠（拖走）的卡片谁都不跟** | 停靠是用户的明确意图 |
| **可见性** | 锚点落在被最小化的祖先里 → **隐藏**，无论是否停靠 | 锚点不在屏幕上，卡片就不该在屏幕上 |

第二条一开始给停靠卡片开了豁免（理由是"它不跟随锚点，所以不必跟着消失"）——
但那是把**位置规则错用到了可见性上**：一张停靠的嵌套卡片会活得比它所解释的文字还久。
现在可见性**只看锚点在哪**。

隐藏是**可恢复**的：卡片留在 state 里，祖先展开后回到原位（停靠位置也保留）。

这条规则要成立，得先解决一个 React 时序问题。

### 子卡片为什么总是晚一拍

`anchorRect()` 是在**渲染期间**读 `range.getBoundingClientRect()` 的。
而 React 的渲染**先于 DOM 提交**——父卡片这一帧已经算出新位置，它的 DOM **还没动**。
子卡片在同一帧去量，量到的是父卡片的**旧几何**，于是永远慢一个提交：
只有等"别的东西"再触发一次重渲染（**滚动、缩放**）它才追上。

这就是"父卡片回到原位时，子卡片要滚一下才跟随"的原因。

**解法**：渲染时把**这一帧实际用的矩形**记进 `placedRectsRef`，
再用 `useLayoutEffect`（**在绘制之前**）在提交后重新量一次；只要发现位移超过 0.5px，
就再渲染一轮——那一轮量到的是已经落定的几何。

`useLayoutEffect` 在 paint 之前执行，所以这次额外渲染**不会被看见**（不闪）。
循环必然收敛：第二轮的矩形已经相等。被停靠的卡片跳过检查——它的位置不依赖锚点。

### 最小化会把子卡片的锚点永久弄坏（更隐蔽的那个）

子卡片的 `Range` 指向**父卡片正文里的一个术语 span**。而最早的最小化实现是直接不渲染整张卡片——
**正文连同它的文本节点一起被卸载**：

1. 子卡片的 `Range` 变成游离节点 → `isAnchored()` 为 false → `anchorRect()` 退化成**固化的旧坐标**
2. 父卡片重新展开时，React 建的是**全新的文本节点**，旧 `Range` 还是指向被扔掉的那些
3. **子卡片再也回不来**了：卡在陈旧位置，标记高亮一起消失

**解法**：最小化一张**内部有东西锚定**的卡片时，卡片节点**保持挂载**，只是
`visibility: hidden` + `pointer-events: none`。

关键不在 `visibility`，而在 **key**：卡片节点无论展开还是收起都保持 `key={card.id}`。
React 对带 key 的子节点是**按 key 复用并移动 DOM 节点**的，所以文本节点会原样活过
"收起 → 展开"这一轮；`visibility: hidden` 又仍然报告真实几何，嵌套锚点因此始终可测量。

> 这里踩过一次坑：第一版给这个隐藏节点用了 `key={card.id + '-ghost'}`。换 key = React
> 卸载旧节点、挂载新节点 = 文本节点照样重建，**整套努力全部作废**。key 才是这个修复的核心。

**这条规则必须对每一级都成立。** 第一版只给"被用户最小化的卡片"保正文，漏掉了
"**因祖先收起而隐藏的卡片**"。于是在 A→B→C 三级嵌套里：收起 A → B 被隐藏 → **B 的正文被卸载**
→ C 的锚点落在一片脱离文档的 DOM 上，照样是死路。

现在判据统一为一句话：**只要"内部有东西锚定"，这张卡片的正文就必须挂载**——
无论它是被最小化，还是被祖先的收起波及。可见与否只由 `visibility` 控制。

配套的两条：

- **内部有东西锚定的最小化卡片，其子卡片会被隐藏**（`hiddenIds`）——它们的锚点在一个看不见的
  父卡片里，画出来只会是一张悬空的卡。它们在 state 里保留，父卡片一展开就回到正确位置。
- **隐藏与停靠无关**：停靠只影响**位置**，不影响**是否存在**。

### 父子关系是**记下来的**，不是渲染时从 DOM 里猜的

判断"谁在谁里面"最初是渲染时反查 DOM：

```js
range.startContainer.closest('[data-explain-card]')
```

**这在最关键的两个场景下必然失效**——而这两个场景恰好就是这套逻辑要处理的对象：

- 祖先被**最小化** → 祖先的正文可能已被卸载
- 祖先被**关闭** → 整棵子树脱离文档

在 A→B→C 三级嵌套里，收起 A 时 B 也会被隐藏并卸载，于是 C 的锚点落在一棵**脱离文档的树**里，
反查要么走到游离节点、要么什么都找不到——**链条从中间断掉**，C 既不隐藏也不跟随。

现在改成**在卡片创建时就把父卡片 id 记进记录**（`parentId`），渲染时直接读。
`readSelection()` 本来就返回 `parentId`，之前只是没往下传：

```js
explain(term, range, rect, { id: card.id, term: card.text, content: card.content })
```

DOM 反查只作为**记录缺失时的兜底**保留。

这一处修正同时修好了三件事：隐藏的传递、关闭的级联、以及正文保留的传递。

### 第三条规则：关闭是级联的

| | 规则 |
|---|---|
| **存在** | 祖先被**关闭** → 自己也**关闭**（不是隐藏） |

关闭 A 会把它从 state 里移除，于是所有指向它正文的 `Range` 全部游离。
**孤儿守卫救不了这个场景**——它的判据是"**全部**卡片都游离时才清理"：

```js
if (cards.length > 0 && !cards.some(isAnchored))
```

只要还剩任意一张正常卡片，B 就会被留下：仍然画在屏幕上，拖拽时的虚线指向一片空白。

> 这个"只在全孤儿时清理"的保守写法本身是为了避免误删（单张卡片的游离可能在 React 换节点时
> 短暂发生），代价就是留下了这个洞。

现在的判据是**结构性**的，不依赖"是否游离"（那是滞后的）：沿每张卡片的**包含链**往上走，
只要链上任何一级**已经不在 state 里**，这张卡片就被清理。

好处：

- **确定性**——不需要等下一次渲染才发现自己成了孤儿
- **一趟传递闭包**——孙卡片也一并处理：它被清理时，父卡片还在，而祖父卡片已经不在
- `parentIdOf` 在**游离的 DOM 树**上依然可用（`closest()` 不要求节点在文档里），
  所以祖先的 DOM 已被移除后，这条链照样读得出来


## 为什么右键菜单是我们自己画的

**这不是偷懒，是平台约束。** DSH 的原生右键菜单由 Electron **主进程**构建，
在 `lib/main.js` 里是一个**硬编码数组**（`window.webContents.on("context-menu", ...)` → `Menu.buildFromTemplate(items)`），
**没有任何注册表或 IPC 扩展点**。渲染进程（插件唯一能存在的地方）无法往里插入条目——这是架构决定的，不是难度问题。

但源码里有个关键细节让这件事变得没有代价：

```js
else if (selectionText.length > 0) items.push({ role: "copy", enabled: editFlags.canCopy });
```

**非编辑区选中文本时，那个原生菜单里只有 `复制` 一项。** 所以我们只接管这一种情形，
等于什么都没丢；编辑框（撤销/剪切/粘贴/全选）和无选中的情形一律不拦截，仍走原生菜单。

```
contextmenu 捕获 → 选中在编辑框内或为空？→ 放行，原生菜单照旧
                 → 否则 preventDefault，画我们自己的菜单
```

颜色方面：**解释、复制、菜单文字读同一套主题令牌**
（`--dsw-alias-label-primary` 文字、hover 用 `--dsw-alias-interactive-bg-hover`），
菜单项共用同一个 `menuItemStyle`，所以它们**不可能彼此不一致**。

## 表面配色：为什么不用 `bg-overlay`

第一版所有表面都用 `--dsw-alias-bg-overlay`，看起来"很土"。从 DSH 自己的主题文件里取出真实色值后，原因很清楚：

| | `--dsw-alias-bg-overlay` | app 自己的层（`bg-base` / `layer-1..3`） |
|---|---|---|
| 亮色 | `rgb(233, 236, 242)` 冷灰 | 全是 **纯白** `rgb(255,255,255)` |
| 暗色 | **`rgb(97, 102, 107)`** 中灰 | `rgb(35,35,36)` / `rgb(44,44,46)` / `rgb(53,54,56)` |

**暗色下卡片比周围亮一倍**——一块惨白的灰板贴在界面上。`bg-overlay` 是给**转瞬即逝的浮层**用的
（系统给它配了 `--dsw-menu-backdrop-filter: blur(40px) saturate(150%)` 去透视背后的内容），
而我们的三个表面都浮在同一片**不透明**界面上，背后没有东西可透视——所以这个令牌从用途上就不对。

同时第一版的边框与阴影是**手挑的数值**，比系统最强档重约三倍：

| | 第一版（手挑） | 设计系统实际定义 |
|---|---|---|
| 阴影 | `0 10px 28px rgba(0,0,0,.22)` | `--dsw-shadow-lv3` 最大一层只有 **`.08`** |
| 边框 | `1px solid rgba(0,0,0,.1)` | `--dsw-elevation-stroke-color`，且系统里用 **`.5px`** 发丝线 |

现在的做法是**改用设计系统自己的高度配方**，不再自己编值：

| 元素 | 背景 | 描边 | 阴影 |
|---|---|---|---|
| 卡片 | `--dsw-alias-bg-layer-3` | `.5px` `--dsw-elevation-stroke-color` | `--dsw-shadow-lv3` |
| 收起后的胶囊 | 同上 | 同上 | `--dsw-shadow-lv2` |
| 右键菜单 | 同上 | 同上 | `--dsw-shadow-lv3` |

`bg-layer-3` 是 app 自己的顶层：亮色为白、暗色为 `rgb(53,54,56)`，
正好落在 `layer-1/2` 之上——**卡片、胶囊、菜单和它们所在的界面属于同一套高度，而不是浮在上面**。

### 菜单一开始是漏网的

第一轮只改了卡片。菜单留着 `--dsw-alias-bg-overlay`，于是变成**白卡片旁边一个灰菜单**——
在亮色主题里尤其刺眼（`rgb(233,236,242)` 的灰紧挨着纯白）。

顺带暴露了第二个问题：**菜单项的 hover 用的是 `--dsw-alias-bg-layer-2`，而它在亮色主题下是纯白**。
菜单本身还是灰底时，hover 只是"稍微变亮"；一旦菜单也换成白底，**hover 状态就彻底看不见了**。
现在改用系统自己的交互令牌 `--dsw-alias-interactive-bg-hover`
（取自 app 自己的 `themeCube:hover` 规则）——它对浅底和深底都成立。

`--dsw-alias-bg-overlay` 和 `--dsw-menu-backdrop-filter` 现在**只出现在注释里**：我们的三个表面都浮在同一片
不透明界面上，背后没有任何东西需要 `backdrop-filter` 去透视。

代价与边界，如实说明：

- 这个菜单是 HTML 画的，**不会和系统原生菜单像素级一致**（原生菜单跟随操作系统主题与字体渲染）。
  换来的是一致于 DSH 应用本身而不是一致于操作系统。
- 若将来 DSH 给那个原生菜单加了别的条目，我们在"选中文本"这一情形下会遮蔽它们。
- 菜单项目前没有做方向键导航（只有 Esc 与鼠标），`role="menu"`/`role="menuitem"` 已就位。

## 原文标记（背景色）

被解释的片段会在原文里留下**背景色标记**，一张卡片一种颜色，所以同时开着的几张解释互不混淆。
**关闭卡片时，该片段的标记随之消失**；收起卡片不取消标记（卡片还在，只是变成胶囊）。

实现用 **CSS Custom Highlight API**（`CSS.highlights` + `::highlight()`）：它按 `Range` 着色，**完全不改动 DOM**。
这是关键约束——官方 practices 明确禁止插件在自己的组件之外写 DOM，
所以不能去把它包成 `<mark>`；Highlight API 是唯一不侵入别人的做法。

- 颜色取自 `MARKER_COLORS`（6 色），创建卡片时用 `pickColorIndex()` 选**当前未被占用**的色号，
  保证同时打开的卡片颜色不重复。
- 颜色是**半透明字面量**而非主题令牌：`::highlight()` 只接受极少的属性集，
  而且低透明度才能在浅色与深色主题下都保持可读。这是有意偏离「只用主题令牌」的一处。
- 卡片 Range 用 `cloneRange()` 快照：创建卡片时会清空浏览器原生选区（好让标记立刻显形），
  克隆保证锚点与标记不受影响。
- 关闭卡片 → `cards` 变化 → 同步 effect 从 `CSS.highlights` 删除对应条目 → 标记消失。
  同步是**按我们的前缀过滤**的，不会碰到别的插件注册的高亮。
- 不支持该 API 的环境自动退化为「无标记」，不做 DOM 兜底。

### 嵌套曾失效的原因（已修）

第一版给**整张卡片容器**也打了 `data-explain-control` 标记，而选区处理器会跳过所有落在该标记内的事件：

```js
if (target instanceof Element && target.closest(`[${CONTROL}]`) !== null) return;
```

本意只想跳过卡片上的按钮，结果把卡片正文一起屏蔽，卡片里选中文字永远不弹触发条。
现在该标记只留在真正的控件上：展开胶囊、收起、关闭、菜单本身与「解释」「复制」两项。

另外两处配套加固：卡片容器显式声明 `user-select: text`（否则可能继承应用外壳的 `user-select: none`），
以及流式期间对未闭合的 `[[术语` 做抑制，避免方括号闪现。

## 改动后的生效方式

**`client.js`（客户端半体）——自动生效，不需要你做任何事。**

`dsh-client-hmr` 每 **500ms** stat 轮询每个客户端 bundle 的 `mtimeMs/ctimeMs/size`，
变化时调 `clientModules.rebuilt(id)`，再通过 SSE 频道 `/plugins/events` 推送
`{type:'rebuilt', id, rev}`；页面侧的 `dsh-client-hmr` 收到后调 `ctx.modules.entries.reload(id, rev)`
**热替换模块**。所以保存文件约 1 秒后新代码就在跑了。

> ⚠️ 顺带一个现象：模块热替换会让 slot 条目重新注册、React 重新挂载，
> 因此**当时打开的卡片会被清空**。这是热更新的正常结果，不是 bug。

**`index.js`（宿主半体）——必须重启应用。**

Cordis 加载器缓存着已求值的 ESM 模块，没有任何热路径能替换它。

### DSH Desktop 里没有"刷新页面"这回事

这一条是纠正早先的错误说法。Desktop 是 Electron 应用，不是浏览器：

- `"刷新页面"`（`role: "reload"`）菜单项写在 `lib/main.js` 的 `...development ? [...] : []` 里，
  而安装版 `development = !app.isPackaged` 为 **false** —— 该项根本不会被创建。
- Windows 上 `Menu.setApplicationMenu` 只挂了 `devToolsItems`（两个 `visible:false` 的 devtools 项 + `F12`），
  应用菜单本身都没装。

所以**没有 Ctrl+R / F5 / Ctrl+F5 可用**。真需要手动重载时，唯一途径是 F12 打开 DevTools 再在其中重载
（DevTools 自己处理该快捷键）。日常不需要：客户端半体自动热更，宿主半体重启应用。

- 缓存只在内存里，模块热更新或重启即失效（若需持久化可换 `sessionStorage`）。
- 模型用当前**默认模型**，不跟随单会话切换。
- 未声明 `Config`；上限与提示词写在 `index.js` 顶部常量里。
- 是否出现可点术语，取决于模型有没有按提示词输出 `[[…]]` 标记；没标记时用选中方式嵌套。
- 卡片**用完即销毁**：切换会话、切换项目、关闭卡片都会永久丢弃。已明确否决保留/归档方案（见第 7 节）。
- 未做术语缓存持久化、整段批量解释。
